   test_agent_run_sse.py:246-266 (test 4) — UNRESOLVED HONESTY QUESTION, shipped as-is.
   `kanban_updated` is emitted on EVERY run reaching status=="completed", regardless of
   `agentName` — a tailoring or cover-letter run (which never touches the board) fires the
   same `kanban_updated` event as a submission run. The payload discloses `basis`/`changes`
   honestly, but the event NAME asserts a board change occurred; test 4 currently locks in
   this behavior for a bare `{status:"completed"}` run with no `output`. Author self-flagged
   UNSURE and did not resolve it. REQUIRED CHANGE: adopt interpretation (b) — withhold
   `kanban_updated` unless `basis=="run_output"` (real jobId/applicationId present); route
   `test-author` (never the fixer, per ADR-GMV4-002's own precedent) to rewrite test 4 to
   monkeypatch a run with real `output`. [VERIFIED-WITH-FRESH-EVIDENCE: code read + test read]

2. apps/api/app/services/agent_run_stream.py:107-112 + apps/api/app/routers/agents.py:2160-2199
   — NO CAP on concurrent SSE streams (per-user or global), while apps/api/app/db.py:8-9
   documents a hard 25-connection ceiling for the ENTIRE application ("The hosted PostgreSQL
   caps concurrent connections at 25... connections are short-lived: open, use, close").
   `get_connection()` (db.py:145-154) opens a brand-new `psycopg2.connect()` per call with NO
   pooling. Each open stream calls `reload_run` (→ one fresh connection) every
   `AETHER_SSE_POLL_SECONDS` (default 1.0s, agent_run_stream.py:112) for up to
   `AETHER_SSE_MAX_STREAM_SECONDS` (default 600s, line 125). No rate limiter is wired to this
   route (`apps/api/app/rate_limit.py` covers only login/register/checkout/portal — grepped,
   zero hits for this route). A handful of users with 2-3 open tabs each can exhaust the
   25-connection global ceiling and degrade/break EVERY other endpoint in the app, not just
   this one. Also: the default poll (1.0s) is 3x TIGHTER than the "2-3s client poll" the
   module docstring (line 8-9) claims to replace (verified actual client poll = 3000ms,
   apps/web/src/lib/api/agents.ts:57) — the replacement claim is not accurate as shipped.
   REQUIRED CHANGE: add a per-user (and ideally global) concurrent-stream cap before this
   route is wired to any UI consumer; document/justify the poll-interval claim or loosen the
   default. [VERIFIED-WITH-FRESH-EVIDENCE: db.py, rate_limit.py grep, agents.ts read]
